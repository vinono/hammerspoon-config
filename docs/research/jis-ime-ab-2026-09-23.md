# Chrome / JIS 输入法自动化复现与 A/B 结果

日期：2026-09-23。环境：macOS 27.0 (26A428)、Chrome 154.0.8037.58、Hammerspoon 1.1.1。

## 已复现的症状

同一个 Chrome 本地普通输入框持续保持焦点：

1. 原配置收到 Eisuu → Kana；输入源 ID 已变为 `com.apple.inputmethod.SCIM.ITABC`。
2. 逐键输入 `nihao` 并按空格，结果为英文 `nihao `。
3. 不切换输入框，再次按 Kana，等待 300 ms 后输入，仍为 `nihao `。
4. 在同一输入框改走系统输入源切换路径，最终确认选中苹果拼音，再次输入得到 `你好`。

关键恢复实验的结果时间（北京时间）：15:46:47 原逻辑失败；15:46:52 单独 Kana 仍失败；15:46:57 系统切换成功。对应 runID：`1790149602.8678`、`1790149607.6477`、`1790149612.5978`。

这复现了“输入源已是中文，但实际英文；再按 Kana 无法恢复”的关键行为。没有自动识别光标旁中/en 提示，不能把输入源 ID 采样说成已验证该提示。

## 测试方式

- 测试页只有普通 input、textarea、contenteditable 和本地事件展示，无网络请求；本次统计使用普通 input。
- Hammerspoon 临时脚本通过原生键码发送 102 / 104 和固定测试字母，不用 DOM fill 或粘贴模拟拼音输入。
- 原配置保持运行，未替换 JIS 回调；A 组经过实际的现有事件处理路径。
- 每次操作前验证前台应用、测试窗口、输入框角色和 `AXWebArea` 的精确本地 URL；离开测试页会停止。
- 每轮读取真实输入框 AXValue，记录输入源、监听启用状态、安全输入状态，以及切换后 20 / 100 / 500 / 1000 ms 的 source ID。
- 网页事件记录也观察到正常拼音时的 compositionupdate / compositionend，最终提交 `你好`。
- 这些是合成原生按键；不等同于物理 JIS 键盘、所有网页、长时间闲置或睡眠唤醒验收。

## 有效对照结果

| 路径 | 条件 | 成功 / 完成次数 |
| --- | --- | --- |
| 原逻辑 Eisuu → Kana | Kana 后约 300 ms 输入 | 5 / 5 |
| 原逻辑：正常拼音下再次 Kana | Kana 后约 300 ms 输入 | 15 / 15 |
| 原逻辑 Eisuu → Kana | Kana 后约 30 ms 输入 | 27 / 31 |
| 原逻辑：捕捉失败后再次 Kana | 同输入框，Kana 后约 300 ms 输入 | 0 / 1 |
| 系统切换并确认目标为苹果拼音 | 最后一次快捷键释放后约 300 ms 输入，含恢复实验 | 6 / 6 |
| 系统切换并确认目标为苹果拼音 | 最后一次快捷键释放后约 30 ms 输入 | 15 / 15 |

31 次快速 A 组包括两批各 15 次以及一次遇到失败即停止的捕捉实验；这不是总体故障率的统计估计。候选路径总计 21 / 21 成功不代表长期零故障。

最初两次失败的 source ID 在切换后 20 / 100 / 500 / 1000 ms 均保持苹果拼音；字母事件发出时也报告拼音。所有已统计失败中 JIS 监听启用，安全输入关闭。仅重启监听或看 source ID 不足以判断恢复。

## 候选路径及校准发现

有效实验路径：先通过 API 选择 ABC，等待约 150 ms；动态创建并依次发送 Control、Option、Space 的按下/释放事件；确认是否到苹果拼音，未到则再发一次。测试中存在三个键盘输入源，不能假设一次轮转必到拼音。

运行时 `hs.keycodes.methods(true)` 返回苹果拼音和豆包拼音。从 ABC 执行一次“下一个输入源”，实际进入豆包；第二次才到苹果拼音。先前研究读取的磁盘偏好文件只列出苹果拼音，不能代替实时状态。

本次校准还发现：

- 仅对 Space 事件附加 ctrl / alt flags，以及 `keyStroke` 的常规发送方式，在本次测试中未切换成功。
- 预先创建 `newKeyEventSequence` 再统一发送的尝试也未达到目标。
- 按文档方式逐个创建、发送修饰键事件再发送 Space，有效触发系统切换。记录显示 flagsChanged 的 ctrl / alt 状态依次建立并释放。
- 早期校准的失败不能与有效候选路径混合统计；3 次输入“你好”但 source 为豆包的试验也不能算苹果拼音验收通过。

这里只记录本机观察，不将上述行为外推为所有版本的 Hammerspoon API 缺陷。

## 结论与生产修复边界

现有 `ime/ime.lua` 在 source ID 已是拼音时直接放行 Kana，确实不能恢复这次捕捉到的故障；直接设置 source ID 成功也不能保证 Chrome 输入上下文已经进入拼音组合输入。证据支持使用系统切换路径作为修复方向。macOS / Chrome 内部具体失效机制尚未证明。

本次完成诊断与候选路径测试，未修改正式 `ime/ime.lua`。临时试验在完成切换后才输入文字，不涵盖用户在整个恢复过程尚未完成时立即打字。因此不能将试验脚本直接安装为日常配置。正式修复还应处理：

1. 多输入源时有界地确认目标；不能硬编码切换一次，亦不能误停在豆包。
2. 同源失效时主动恢复，保持 Kana 单向进入中文的语义。
3. 处理切换期间的键入、已有组合文本、快速 Eisuu 取消，以及窗口/焦点变化，避免文字丢失或延迟回切。
4. 对实际 Kana 触发的修复入口复跑本报告中的失败场景；不能仅测独立的恢复函数。
